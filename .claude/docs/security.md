### Security posture: development vs production mode

`ktor.development` is env-overridable (`$KTOR_DEVELOPMENT:true`): local `:server:run`/tests default to development mode; **the Docker image ships `KTOR_DEVELOPMENT=false`** (production mode), and `docker-compose.yaml` explicitly sets it back to `true` because it is the local plain-HTTP demo. Production mode activates HSTS + HTTPS redirect and three **fail-closed startup checks**:

- **JWT secret** (`plugins/Security.kt`): blank, the placeholder `"secret"`, the repo-committed compose demo key (`dev-only-00366d…`), or the `k8s/secret.yaml` template placeholder (`CHANGE-ME-openssl-rand-hex-32`) → warn in development, **refuse to start** in production. Set a strong private `JWT_SECRET`.
- **Seed passwords** (`infra/db/Bootstrap.kt`, module `configureBootstrap`, runs after `configureDatabase`): in production mode, if any active account still carries the well-known `changeme` bcrypt hash the app **refuses to start**. Setting `ADMIN_INITIAL_PASSWORD` (config `bootstrap.adminInitialPassword`) rotates the V3 seed admin's password at startup — idempotent: only applied while the admin still has the seed hash, so an admin-chosen password is never overwritten. Covered by `BootstrapTest`; seed-mutating tests restore state via `TestSeedState.restoreSeedAccounts()` (`TestEnvironment.kt`).

- **Mail transport** (`infra/mail/Mail.kt`): `mail.transport=log` writes outbound email (including generated passwords) into the application log — permitted with a warning in development, **refuse to start** in production; `smtp` with a blank host refuses to start in **any** mode. See "Outbound email" below.

- **Data-encryption key** (`infra/crypto/Crypto.kt`, module `configureCrypto`, right after `configureMail` and BEFORE `configureDatabase`): blank or one of the two burned repo-committed keys (`DEV_DATA_ENCRYPTION_KEY` — the application.yaml default — and `COMPOSE_DATA_ENCRYPTION_KEY`) → warn in development, **refuse to start** in production; a malformed key (not 64 hex chars — the k8s template placeholder included) refuses in ANY mode. See "Encryption at rest" below. Covered by `CryptoBootTest`; every production-mode boot test overrides `security.encryption.key` with `strongEncryptionKey()`.

**JWT model** (`auth/Tokens.kt` + `plugins/Security.kt`): login issues an access/refresh **pair**, both carrying `email`, `userId`, a `roles` array, a `typ` claim (`"access"`/`"refresh"`), and a random `jti`. The `jwt {}` verifier requires audience (`covenant-api`), issuer (`http://0.0.0.0:8082/` by default), `typ == "access"`, and a PRESENT `jti` absent from the DB-backed blocklist (a jti-less token could never be revoked, so both the verifier and `/refresh` reject it outright) (`auth/TokenBlocklistService.kt`, table `revoked_tokens` — `/logout` writes it, the revoke path prunes expired rows). Blocklist verdicts are served through a 30-second in-memory cache (`REVOCATION_CACHE_TTL_MS`) so the per-request check is not a DB round-trip; `revoke()` seeds its own instance, so on this single-replica deployment a logout is visible immediately and the TTL only bounds staleness across a restart (covered by `TokenBlocklistCacheTest`). Full token/refresh/logout semantics: see "Authorization model" in `.claude/docs/authorization.md`.

**Token storage & response headers (the XSS posture).** The SPA keeps BOTH tokens in `localStorage` under `covenant.auth.*` (`web/src/api/session.ts` — access, refresh, roles, userId, disabledFeatures; no password is ever persisted; everything else in localStorage is view state). A deliberate trade-off, documented rather than hidden: any script running on the origin can read the REFRESH token, i.e. a renewable session unbound to device/IP whose only revocation is `/logout` — so the real control is keeping foreign script out. That control is `plugins/SecurityHeaders.kt`, installed unconditionally and pinned by `ServerTest`: a strict CSP (`script-src 'self'`, `object-src 'none'`, `base-uri 'self'`, `frame-ancestors 'none'`), `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`. Consequences: never weaken `script-src` (no CDN scripts, no `unsafe-inline` — Vite bundles everything same-origin, fonts included), and the SPA must stay free of `dangerouslySetInnerHTML`/`eval` sinks (currently zero). Moving tokens to httpOnly cookies would trade this for CSRF machinery — revisit only with that full picture.

**Login timing equalizer** (`auth/AuthRoutes.kt` + `TIMING_EQUALIZER_HASH` in `auth/Passwords.kt`): an unknown email pays a full, discarded bcrypt verify against a fixed cost-12 hash so its 401 takes as long as a wrong password's — without it, response timing is an account-enumeration oracle (the reset path equalizes via async processing; login equalizes in-line).

**Per-account login lockout** (`auth/LoginThrottle.kt`, wired in `configureAuthRoutes`): after `security.lockout.threshold` (default 5, `$LOGIN_LOCKOUT_THRESHOLD`) consecutive failures for one submitted email, `/login` answers `429` for `security.lockout.durationSeconds` (default 900, `$LOGIN_LOCKOUT_DURATION_SECONDS`) — even with the correct password, and regardless of whether the account exists (no enumeration signal). A success resets the counter. In-memory and per-instance by design (single-replica deployment; a restart only resets the throttle). Complements the per-IP `RateLimit` bucket, which rotating hosts sidestep. The lockout 429 is **thrown** (`TooManyRequestsException`), never `respondProblem`ed directly — StatusPages' generic 429 status handler rewrites any non-StatusPages 429, so only the exception path keeps the specific detail. Tests: `LoginThrottleTest` (unit, injected clock) + `LoginLockoutTest` (route). The SPA maps the 429 to `auth.accountLocked`.

**Self-service password reset** (`POST /api/v1/password-reset`, in `auth/AuthRoutes.kt`; SPA: "Forgot password?" on `/login` → `/reset-password`): body `{email}`; always `202` for a well-formed request — account existence is unobservable (the lookup/generate/send/store work runs **asynchronously** after the response, so latency is uniform too). If the account exists, a new 16-char password is generated server-side (`generatePassword` in `auth/Passwords.kt`, 96 bits), the email is sent **first** and only then the bcrypt hash stored via `UserService.updatePassword` (a delivery failure leaves the old password working); the `password_changed_at` stamp invalidates outstanding refresh tokens. Throttled per submitted email — one request per `security.passwordReset.minIntervalSeconds` (default 60, `$PASSWORD_RESET_MIN_INTERVAL_SECONDS`) — uniformly for existing and unknown addresses (`auth/PasswordResetThrottle.kt`, in-memory/per-instance like the lockout), plus a per-IP `RateLimit` bucket (`security.rateLimit.passwordResetPerMinute`, `$PASSWORD_RESET_RATE_LIMIT_PER_MINUTE` — blank follows the mode: 5/min production, 100/min development, the loginPerMinute rationale; back-to-back e2e runs from one host would otherwise trip it). `503` when the deployment has no outbound email (`MAIL_TRANSPORT=disabled`). A soft-deleted account is unknown here by construction (`findWithIdByEmail` filters active rows). The email renders through the `LocalizedText` catalog (`infra/mail/PasswordEmail.kt` + `auth/PasswordResetEmail.kt`) in the RECIPIENT'S stored language (V1 `users.language`, EN fallback), includes a sign-in link only when `mail.appUrl` is set, and warns the recipient that their previous password no longer works. Tests: `PasswordResetThrottleTest` + `LocalizedEmailTest` (unit) + `PasswordResetTest` (route, incl. the full email→login roundtrip via a `ListAppender` on the `ch.nokillswit.mail` logger and the send-before-store delivery-failure case).

**Per-IP login bucket** (`security.rateLimit.loginPerMinute`, `$LOGIN_RATE_LIMIT_PER_MINUTE`; every bucket is installed by `plugins/RateLimits.kt`, which also owns the bucket names): blank **follows the mode** — 10/min in production, 1000/min in development — and an explicit number pins it in either mode (the `http.exposeOpenApi` idiom). Development is lifted because the e2e suite drives its logins from one host and would otherwise sleep out the bucket; **the per-account lockout above is the actual brute-force defence and is identical in both modes**. The sibling `refresh` bucket defaults to 30/min in both modes and is pinnable via `security.rateLimit.refreshPerMinute` (`$REFRESH_RATE_LIMIT_PER_MINUTE`). `RateLimitResponseTest` and `LoginTest` pin the value to `10` explicitly, since tests run in development mode.

**Email MFA (opt-in)** (`auth/MfaChallenges.kt` + `auth/MfaEmail.kt`, wired in `configureAuthRoutes`): a per-user second factor behind the `MFA` feature flag — **the one inverted-default flag**: `V5` seeds every existing user as MFA-disabled and `UserService.create` inserts the disabled row for every new user (admin create and test seeds both funnel through it), so MFA is OFF until an admin removes the row via the features PUT (the per-user editor or the `/feature-flags` bulk screen; mind the wholesale-replace semantics — a PUT whose disabled set omits `MFA` ENABLES it, including the "empty array re-enables everything" idiom). With MFA enabled, `POST /login` with correct credentials answers `200 MfaChallengeResponse {mfaRequired, challengeId, expiresAt}` instead of tokens (the branch runs AFTER `verifyPassword`, so nothing about enumeration or lockout changes; `login.success` is deliberately NOT emitted); a 6-digit code (`generateMfaCode`, `auth/Passwords.kt`) is held in the in-memory challenge store (config `security.mfa.codeTtlSeconds` default 300 `$MFA_CODE_TTL_SECONDS`, `security.mfa.maxAttempts` default 5 `$MFA_MAX_ATTEMPTS`; per-instance like the throttles — a restart just means signing in again) and emailed in the user's stored language (V1 `users.language`, EN fallback). `POST /api/v1/login/mfa` `{challengeId, code}` (own per-IP bucket `"mfa"`, hardcoded 10/min in every mode) exchanges it for the ordinary `LoginResponse` — one fresh `userService.read` first (the `/refresh` precedent: current roles/flags; a user deleted in between → the uniform 401 `user_gone`); every failure mode (unknown/expired/wrong code/attempt cap) is a **uniform 401**, reasons live only in the `login.mfa_failure` audit event; challenges are single-use. **Mail-less deployments fail closed**: on `MAIL_TRANSPORT=disabled` an MFA-enabled login answers `503` (`login.mfa_unavailable`) — don't enable MFA flags on the k8s default `disabled` transport; the features PUT keeps working, so an admin can always flip a flag back. SPA: the Login card's second step (`PinInput`, `auth.mfa*` keys). Tests: `MfaChallengesTest` (pure store) + `MfaLoginTest` (route matrix); e2e `mfa.spec.ts` drives the emailed code through Mailpit.

**Swagger/OpenAPI gate** (`plugins/Http.kt`): `/openapi` (UI + spec) is served only in development mode, or when `http.exposeOpenApi` (`$HTTP_EXPOSE_OPENAPI`) is explicitly `"true"` — blank follows the mode, `"false"` hides it even in dev. Bearer auth cannot protect a browser-loaded UI (page loads carry no `Authorization` header), hence a gate rather than `authenticate {}`.

**Accounts are admin-managed.** There is no self-signup: administrators create accounts at `/users/new`. The initial password is generated CLIENT-side (`web/src/utils/password.ts`, 96 bits) and shown to the admin exactly once in the reveal modal — the server stores only the bcrypt hash and no response ever carries plaintext; users rotate it via the Change password page (the existing `PUT /users/{id}/password` rules). Deletion is the soft-delete convention plus two guards: no self-delete (403) and the last active administrator can be neither deleted nor demoted (409).

**Canonical email identity.** Emails are folded to `trim().lowercase()` (`canonicalEmail` in `users/Validation.kt`) at EVERY entry point — login and `findWithIdByEmail` itself (defense-in-depth) today, and every future create/update/import — so one mailbox is one account and a padded/case-variant login matches (and shares one lockout bucket). The V1 partial unique index stays byte-wise (all writes are canonical).

**Request body ceiling.** `RequestBodyLimit` (installed in `plugins/Http.kt`, `MAX_REQUEST_BODY_BYTES` = 10 MiB) rejects oversized bodies with a 413 problem (mapped in `plugins/ErrorHandling.kt`) before any receive/validation work — a memory-DoS backstop, not a business rule; field-level `maxLength` validation rejects oversized values far earlier on ordinary payloads. Declared in the spec on the body-heavy operations (users create today; the contract-version create/content/import routes when they land — a document is capped at 2 MiB by its own `contracts.maxDocumentBytes` rule, well under the backstop) and covered by `PayloadValidationTest`.

**Request payload validation (convention — API-SEC-003/API-ERR-005).** Mutating routes validate payloads up-front and throw `BadRequestException` (→ `400` + `ProblemDetail`) instead of letting oversized/blank values die in the DB as `500`s. One cross-cutting example: password ≥ `MIN_PASSWORD_LENGTH` (10) chars AND ≤ 71 UTF-8 bytes (`validatePassword` in `users/UserRoutes.kt` + `MAX_PASSWORD_BYTES` in `auth/Passwords.kt` — **the bcrypt ceiling**: longer input makes bcrypt throw, and the 500-vs-401 split would be an account-enumeration oracle, so login's `verifyPassword` guards it too). Declare limits as `maxLength` in the OpenAPI spec. Keep new validators feature-local and enforce them **after** the authz guard (403 wins over 400). Covered by `PayloadValidationTest`.

**Outbound URL fetch (SSRF posture).** `contracts/UrlFetch.kt` (Toadie's `catalog/UrlFetch.kt`, ported verbatim; its route is `POST /api/v1/contracts/fetch`, the import page's fetch) makes the server issue outbound requests on user command — the import page's fetch-from-URL of a contract document from a Git host. Guards, in order: absolute `https` only, no userinfo, non-blank host ≤ 2048 chars (`parseFetchUrl`); then every resolved address must be public — loopback, site-local, link-local, any-local, multicast, IPv6 unique-local `fc00::/7` (NOT covered by `isSiteLocalAddress`), CGNAT `100.64.0.0/10`, `192.0.0.0/24`, benchmarking `198.18.0.0/15`, and NAT64 `64:ff9b::/96` addresses embedding a non-public IPv4 are refused, unresolvable hosts too (`requirePublicHost`). Every guard rejection is the **uniform 400** `FETCH_URL_INVALID_DETAIL` (never echoing what was probed) and audited as `contract.fetch_blocked` with scheme/host ONLY (a URL may embed query-string tokens — never log the full URL); a SUCCESSFUL fetch leaves the same-shaped `contract.fetched` trail, so the security log records who had the server pull from where, not only what it refused. The JDK `HttpClient` runs with `followRedirects(NEVER)` (following one would bypass the address check — load-bearing), 10 s timeouts, and a bounded 1 MB body read (`readNBytes`, never `ofString`); upstream failures (non-200, redirect, oversize, unreachable) are `BadGatewayException` → 502. **Accepted residual risks**: the resolve-check-then-connect gap (DNS rebinding) — closing it needs custom socket plumbing, out of proportion here; a stored source URL (V12's `contract_versions.source_url`, the sync feature's reference) is served in full to every authenticated user and rides the contract's history as an event param — don't put secrets in source URLs (the audit trail logs the host only); and the 502 detail echoes the upstream HTTP status (useful for diagnosing a broken reference, and only reachable for PUBLIC hosts the guard already admits). The `ContractUrlFetcher(urlValidator)` seam exists ONLY so tests can point the response handling at a 127.0.0.1 fixture server; production wiring always uses the default `validateFetchUrl` chain (`UrlFetchTest` pins the guard matrix; the route tests return with the route).

**Outbound connections to environments — the try-it trust boundary (`contracts/tryit/`, milestone 3c).** The try-it feature makes the server call a REAL system on user command — an HTTP request to an OpenAPI operation, a Kafka publish/read, a read-only SQL sample — through an **Environment** (`environments/`, ADMIN-curated per System, secrets encrypted at rest). This is deliberately NOT the URL-fetch posture above: an environment's host is typically internal (`gateway.internal`, `kafka:9092`, `postgres:5432`), so `requirePublicHost` would defeat the feature; the trust boundary is the registry itself — only an ADMIN may register a target (`TargetValidation.kt`: http(s) only, no userinfo/query/fragment, link-local literals refused, 1–20 bootstrap `host:port` entries, a JDBC URL whose parameters are limited to an allow-list, so a URL can never smuggle a socket factory or a logger file), and every user may then aim a try at it — a regular user gains no reach an ADMIN did not grant. What stays load-bearing on the call itself (`HttpTry.kt`): the environment's base URL REPLACES the document's `servers[]` (the document contributes method + path template only — an operation it declares, TRACE never, every `{param}` bound and percent-encoded); redirects are never followed (a 3xx is the observation); request and response bodies are bounded at 1 MiB (a bigger request is `413`, a bigger response is shown truncated and not validated); the caller's `Host`/`Content-Length`/`Transfer-Encoding`/`Connection`/`Upgrade`/`TE`/`Trailer`/`Keep-Alive`/`Expect`/`Cookie`/`Proxy-*` headers are refused (`400` naming the header), header names must be tokens and values CRLF/NUL-free, at most 20 headers and 50 query parameters of ≤ 4 KiB; the response's `Set-Cookie*` and hop-by-hop headers are dropped and at most 50 are returned. **The caller MAY type credentials into the per-call headers** (a bearer token for the operation's security scheme) — they are forwarded to the target and then forgotten: never stored, never in the audit (`contract.tried_http` carries byUserId/contractId/versionId/environmentId/host/method/pathTemplate/status/durationMs/outcome — never headers, bodies, the substituted path or the query string, which may embed a token), and the response's `url` is returned without its query. A target that cannot be reached (connect/read timeout 10 s, TLS failure, refused) is a uniform `502` "The environment could not be reached"; whatever the target answers — 4xx/5xx included — is a `200` here with the status shown. The four try POSTs share one per-IP `RateLimit` bucket (`tryIt`, `security.rateLimit.tryPerMinute` / `$TRY_RATE_LIMIT_PER_MINUTE`, default 60/min in both modes, installed with the other buckets by `plugins/RateLimits.kt`), nested INSIDE `authenticate {}` so an anonymous probe is a 401 that spends no token. Tries reach the SECURITY audit only, never `contract_events` (an observation is not a change to the contract). The SQL leg (`SqlTry.kt`, ODCS) runs **no user-written SQL**: the dataset must be one the document declares (a table or a view — its `physicalName`, else `name`, is the relation read, never the caller's spelling), the identifier is validated against `[A-Za-z_][A-Za-z0-9_$]{0,62}` (optionally schema-qualified) and quoted, the statement is the fixed `SELECT * FROM <relation> LIMIT ?` with the limit (1–200) bound; the JDBC connection is read-only at three levels (driver `readOnly`, `readOnlyMode=always`, `SET TRANSACTION READ ONLY`), capped by `SET LOCAL statement_timeout = '15s'`, 5 s connect / 20 s socket timeouts, `ApplicationName=covenant-try`, and rolled back in every case; cells are cut at 4 KiB and the sample at 1 MiB, `bytea` comes back as base64. A missing relation (`42P01`) is an observation (`DATASET_MISSING`); privilege (`42501`), credential (`28xxx`), timeout (`57014`) and connection failures are classified `502` details that never echo the URL or the credentials. The Kafka leg (`KafkaTry.kt` + `KafkaClients.kt`, AsyncAPI): the client configuration is built ONLY from the environment's enumerated fields — bootstrap servers, security protocol, SASL mechanism, username, password — and the `sasl.jaas.config` line is COMPOSED server-side naming one of the two Kafka-bundled login modules (`PlainLoginModule`/`ScramLoginModule`, values quoted with `"` and `\` escaped); **no request and no registry field ever carries a JAAS string or a Kafka client property** (a caller-chosen login module is the CVE-2023-25194 class). Publish is **contract writers only** (`authorizeWrite` BEFORE the body decodes) — the one try that mutates a real system with the environment's stored principal — idempotent producer, `acks=all`, a 256 KiB payload cap (`413`), 10 s delivery timeout, the topic = the channel's literal address (templated → `400`). Read runs with **no consumer group** (nothing committed, no trace on the cluster), `allow.auto.create.topics=false` (an unknown topic is a `502`, never a created one), a 1–50 tail over every partition inside a 5 s budget, payloads cut at 64 KiB (base64 when not UTF-8). Both clients close with a 2 s bound so a wedged broker never holds a request thread. Failures are classified `502` details (credentials refused / principal may not access the topic / topic missing / record too large / unreachable) that never echo the JAAS line. Audits `contract.tried_kafka_publish` (bootstrap/topic/partition/offset) and `contract.tried_kafka_read` (bootstrap/topic/count) — never a payload, key or header. The demo compose Postgres role is read-write — production environments should carry a READ-ONLY database role (the connection's read-only mode is a guard, not a substitute). Audit `contract.tried_sql`: byUserId/contractId/versionId/environmentId/host/dataset (the quoted relation)/rowCount/durationMs/outcome — never a cell. **Accepted residual risk**: an ADMIN can point an environment at any host the server can reach — that is the feature; the audit trail records who tried what against which environment. Tests: `TryHttpTest` (a 127.0.0.1 `HttpServer` fixture is a legal environment, so no seam is needed), `TrySqlTest` (a fixture table + view in the shared Testcontainers database registered as an environment), `TryKafkaTest` (a KRaft `apache/kafka-native` container via `KafkaTestSupport`) and `KafkaTryConfigTest` (the JAAS composition and escaping).

**The inference engine's observe legs (`contracts/infer/`, release 0.8.0) sit on the SAME trust boundary and the SAME code as try-it above** — they pull ONE live sample through an Environment for the inferencer to build a draft from, never a document to check against. `POST …/infer/observe/http` runs through `HttpTry.send` after a leaner `HttpTry.prepareRaw` (the caller's own method and a literal path, no `{template}`, under the identical header/body static rules and the identical 1 MiB bounds); the response reduces to the wire shape's `HttpExchangeSample` — header NAMES only, the `Authorization` value's scheme word kept and nothing else, the body dropped past 1 MiB (`INFER_BODY_SKIPPED`). `POST …/infer/observe/kafka` runs the unchanged `KafkaTry.read` (bounded tail, no consumer group) over a topic the caller names directly (`^[A-Za-z0-9._-]{1,249}$`, never a document's channel), reducing the records to their UTF-8 JSON payloads only — a tombstone, a binary or a truncated record is dropped and the drop counted in one `INFER_RECORDS_SKIPPED` note. `POST …/infer/observe/sql` and its `…/sql/relations` sibling replace `SqlTry`'s `SELECT * FROM <dataset> LIMIT n` with **fixed `pg_catalog` queries** (`to_regclass`, `pg_attribute`, `pg_index`) — never `SELECT *`, never a caller-composed statement — over the SAME read-only connection prologue, now shared as `contracts/tryit/PostgresRead.kt` (`readOnly(target) { … }`: connect, `SET TRANSACTION READ ONLY` + a 15 s `statement_timeout`, roll back in every case; `classify(SQLException)` the one 502-detail mapping both legs share). The relation identifier follows the exact grammar `SqlTry.prepare` uses (`SqlTry.IDENTIFIER`, optionally schema-qualified); a relation `to_regclass` cannot resolve is a `404`, never a 502. All four observe legs ride the SAME `tryIt` per-IP `RateLimit` bucket as try-it, nested inside `authenticate {}`, and need only authentication (any user who may aim a try-it call may pull an observe sample — no `canWrite`, since nothing about a contract is touched; the draft is saved through the ordinary version-create path, where the writer guard applies). Audited as `contract.observed_http` (byUserId/environmentId/host/method/status/durationMs/outcome), `contract.observed_kafka` (byUserId/environmentId/bootstrap/topic/count/outcome) and `contract.observed_sql` (byUserId/environmentId/host/relation — the quoted identifier, null when listing —/columnCount or count/outcome) — the SAME never-logged set as try-it: no path, query, header, body, payload or cell ever reaches the trail.

**The checker sidecar (`checker/`).** Contract lint/semantic checks run in a separate Node service (Spectral + `@asyncapi/parser`) that the SERVER calls (`contracts/checks/CheckerClient.kt` → `POST http://checker:9090/check`); the SPA never reaches it. Posture, in layers: (1) **network isolation** — the compose service sits on the `internal: true` `checker-net` only (no host port, no default gateway → no route to the internet), the k8s twin is a ClusterIP service behind a `NetworkPolicy` allowing ingress from the app pod only and no egress; (2) the checker **pre-scans every `$ref`** in a document and refuses external ones as a finding WITHOUT resolving anything — load-bearing, because `@asyncapi/parser`'s resolver cannot be told to drop its default http/file readers; (3) an optional shared secret (`CHECKER_TOKEN`, sent as `X-Checker-Token`, compared in constant time) as the second fence; (4) the container runs as the unprivileged `node` user with a read-only root filesystem, a 2 MiB body cap and a 20 s per-request budget. The server treats the checker as **fail-open for LINT** — unreachable/timeout/non-2xx yields one report-only `CHECKER_UNAVAILABLE` finding and the operation proceeds on the JVM's own syntax/schema verdicts (which stay fail-closed); the checker's verdicts are DATA (findings rendered by the SPA), never executed. A user document is untrusted input on both sides: the JVM's YAML parser runs with a code-point limit and the default alias caps (alias bombs), the JVM validators never resolve remote `$ref`s (`ParseOptions.setResolve(false)`, networknt with no remote schema loaders), and document text is stored byte-exact but never interpreted beyond parsing. See `.claude/docs/checker.md`.

**CORS is off by default** (`plugins/Http.kt`): the plugin is installed only when `http.corsHosts` (`$CORS_ALLOWED_HOSTS`, comma-separated hosts) is non-empty. Production is single-origin (Ktor serves the SPA) and dev goes through the Vite proxy, so no cross-origin caller exists by default — no `anyHost()`. **Reverse proxy**: set `HTTP_BEHIND_PROXY=true` (config `http.behindProxy`) when TLS terminates at an ingress/proxy — it installs `XForwardedHeaders` so rate-limit buckets key on the real client IP and the HTTPS redirect sees the real scheme; the proxy must set (and strip client-supplied) `X-Forwarded-For`/`X-Forwarded-Proto`. Off by default because honoring those headers from direct clients lets them spoof both.

CSRF install is gated behind `security.csrf.enabled` (default **`false`** in `application.yaml`, env-overridable via `SECURITY_CSRF_ENABLED`); the configured `originMatchesHost()` + `allowOrigin("http://localhost:8082")` + `checkHeader("X-CSRF-Token")` combo is unsatisfiable from both the Ktor test client and the dev SPA on `:5175`, and CSRF protection is anyway moot for this app's bearer-JWT auth model — browsers do not auto-attach `Authorization` headers, so cross-site forms cannot forge an authenticated request. Re-enable only if you move to cookie-based session auth and fix the allow-list accordingly.

**Default admin.** Migration `V3__seed_admin.sql` inserts a single bootstrap administrator on first boot: `admin@covenant.local` / `changeme` (role `ADMIN`), idempotent via `ON CONFLICT DO NOTHING`. The migration is kept **unchanged** (dev + e2e depend on it; checksums must not change) — production neutralizes it at startup via the bootstrap above. There are no demo seed users (Lettuce's V9 demo org was not ported). **Kubernetes secrets** live in the `covenant-secrets` Secret in the `covenant` namespace (`k8s/secret.yaml` is a placeholder template — create the real one out-of-band with the `kubectl create secret generic` command in its header; the app deployment consumes it via `secretKeyRef`).

**Outbound email** (`infra/mail/`, ported from Lettuce): `configureMail` (registered at the top of the infrastructure group, before Flyway) publishes `MailerKey` holding a `Mailer` or null. `mail.transport` (`$MAIL_TRANSPORT`) selects `log` (dev default — the full message, **including generated passwords**, goes to the `ch.nokillswit.mail` logger; **production mode refuses to start on it**), `smtp` (Jakarta/Angus Mail over `mail.smtp.*` / `$SMTP_HOST` etc.; a blank host refuses startup in any mode), or `disabled` (the Docker image default via `ENV MAIL_TRANSPORT=disabled` — email features answer 503 through `respondMailUnavailable`). The compose demo wires `smtp` → the bundled Mailpit (`http://localhost:8027` — 8025 is Lettuce's, 8026 Toadie's); k8s ships `disabled` with `SMTP_USER`/`SMTP_PASSWORD` read (optional) from `covenant-secrets`. Consumers: self-service password reset and email MFA. The recipient-language content layer (`LocalizedText`/`passwordEmail`) lives beside the transports. Tests: `MailTransportTest` (the transport matrix + both refusals + LogMailer delivery via the `ch.nokillswit.mail` LogCapture); production-mode boot tests must override `mail.transport` with `"disabled"`, since the dev-default `log` transport is refused in production.

**Encryption at rest** (`infra/crypto/`, Lettuce's, ported verbatim). Sensitive columns are encrypted application-side with AES-256-GCM (`FieldCipher`: a fresh 12-byte nonce per value, 128-bit tag, envelope `enc:v1:<base64(nonce||ciphertext)>`), so a database-level attacker — SQL access, `pg_dump`, a stolen volume or backup — sees ciphertext; the key lives with the app (`DATA_ENCRYPTION_KEY`, 64 hex chars from `openssl rand -hex 32`; compose ships a burned demo key, k8s reads `covenant-secrets`), never in the database. **Losing the key loses every encrypted value** — back it up apart from the DB. Rotation: set the OLD key as `DATA_ENCRYPTION_KEY_PREVIOUS` (decrypt-only fallback — a wrong-key attempt fails cleanly on GCM's tag, then the previous key is tried) and the new one as `DATA_ENCRYPTION_KEY`, boot once (the bootstrap backfill re-encrypts every row under the current key), then remove the previous key. Rows written before a column was encrypted (legacy plaintext, returned unchanged by `decrypt`) are encrypted once at the next boot by the same backfill (`reencryptRows`, selecting through the ONE sanctioned SQL predicate over an encrypted column: `notLike "enc:v1:%"`). A service owning encrypted columns implements `EncryptedAtRest` and is registered in `infra/db/Bootstrap.kt`'s `encryptedAtRestServices()` list — never remove a registration (a rotation would strand that feature's rows). **Never filter or sort on an encrypted column in SQL** — ciphertext carries no order or equality (every value has its own nonce). Encrypted today: the try-it environments' `kafka_password` / `pg_password` (milestone 3c). Tests: `FieldCipherTest` (roundtrip, fresh nonces, legacy passthrough, tamper, wrong key, rotation, malformed keys), `CryptoBootTest`, and each owning feature's `*EncryptionTest` asserting the raw column holds an envelope and the backfill/rotation work.
