### The checker sidecar (`checker/`)

The 500-entry response cap includes its truncation marker: a truncated response contains at
most 499 engine findings followed by one `findings-truncated` SYSTEM/INFO entry.

The JavaScript contract tooling — **Spectral** (`@stoplight/spectral-core` + `-rulesets` `oas`/`asyncapi`) and **`@asyncapi/parser`** — has no JVM equivalent, so it runs as a small Node 24 + TypeScript service the SERVER calls; the SPA never talks to it, and the browser never bundles it. It is stateless, ESM, plain `node:http` (no framework), mirrors `web/`'s toolchain (TypeScript ~6, eslint + sonarjs, knip, vitest), and ships as its own image (`checker/Dockerfile`, 2-stage, non-root, read-only root filesystem).

**Contract (`checker/openapi.yaml` — reviewed with `/api-review` like the main spec).** `POST /check` with `{type: "OPENAPI"|"ASYNCAPI"|"ODCS", content: string, previousContent?: string}` → `200 {findings: Finding[], engine: [{name, version}]}`, findings sorted severity → line → code and capped at 500 (a final INFO `findings-truncated` marks the cut). `GET /healthz` → `{status: "ok", engines: [...]}` (the Docker/k8s probe). Errors are RFC 7807 problem bodies like the main API: `400` malformed/unknown-member request or unknown type, `401` on an `X-Checker-Token` mismatch (constant-time compare; skipped when `CHECKER_TOKEN` is unset), `413` above the whole-request body cap (checked on `Content-Length` AND while streaming), `415` when `Content-Type` is not `application/json`, `503` when the bounded check queue is full, and `504` when the queue plus engine work exceeds the per-request budget. Every problem body includes the request path as `instance`. Env: `PORT` (9090), `CHECKER_TOKEN`, `CHECKER_MAX_BYTES` (8 MiB + 1 KiB by default: two 2 MiB documents, two-byte JSON escaping, and an envelope margin), `CHECKER_TIMEOUT_MS` (20 000), `CHECKER_MAX_CONCURRENT` (1), `CHECKER_MAX_QUEUED` (8), `SCARF_ANALYTICS=false` (Spectral's `@scarf/scarf` postinstall phones home — opted out in the Dockerfile, CI and every documented `npm ci`). The JVM owns the per-document UTF-8 cap; when `CONTRACT_MAX_DOCUMENT_BYTES` is changed from 2 MiB, set `CHECKER_MAX_BYTES` to at least `4 * CONTRACT_MAX_DOCUMENT_BYTES + 1024` so a maximally escaped candidate and AsyncAPI baseline still fit.

**Engines and what each catches.** `OPENAPI` → Spectral with the `oas` ruleset (`oas3-schema` = structural validation → SCHEMA; every other rule → LINT); a `swagger: "2.0"` root is refused as `unsupported-version` (the JVM's type gate refuses it first). `ASYNCAPI` → `@asyncapi/parser` `Parser().validate(content)` (its own ruleset: `asyncapi-schema`, channel/operation/server/security consistency → SEMANTIC; the "No schema parser registered" warning is filtered for `application/vnd.apache.avro*` payloads — the JVM validates Avro) PLUS Spectral's `asyncapi` ruleset (v2 and v3 aware → LINT), deduplicated by `(code, path)`. `ODCS` → accepted, returns no findings (the JVM's JSON Schema validation is the whole ODCS gate — a standing decision; a custom Spectral ruleset for ODCS would be a cheap add if lint for it is ever wanted). `previousContent` (ASYNCAPI only — the JVM sends the ACTIVE baseline's text it chose, never for other types) adds the **`@asyncapi/diff`** pass (`engines/asyncapi.ts` `breakingAsyncApi`): valid self-contained texts go through the parser (dereferenced `document.json()`), Avro schema subtrees are replaced with the same opaque marker in both comparison models (including dereferenced copies) so the JVM can apply Apache Avro reader/writer rules, the standard's `/info/version` edit is overridden to non-breaking (every candidate edits it), `x-parser-*` paths are dropped, and each breaking change is one `BREAKING` fact `breaking-add|remove|edit` at its pointer (minted WARN — the JVM settles WARN vs INFO by the MAJOR bump and adds its gate); a pair the differ refuses (two AsyncAPI majors, an unparseable baseline) is one INFO `asyncapi-diff-skipped`, never a failed check. **Severity map** (`checker/src/findings.ts`, the only place): Spectral `DiagnosticSeverity` Error=0 → ERROR, Warning=1 → WARN, Information=2 and Hint=3 → INFO; **source map**: `parser` → SYNTAX, `*-schema`/`invalid-ref`/`asyncapi-3-document-*` → SCHEMA, everything else → LINT (parser-only codes → SEMANTIC); positions 0-based → 1-based; Spectral's `path` array → a JSON pointer. The JVM never re-maps — it stores what the checker says. Compatibility treats a truncated checker response as incomplete comparison coverage, since severity-first capping can discard BREAKING findings.

**Offline, in two layers — WHY both.** The parser libraries resolve `$ref`s: Spectral takes a `Resolver` with no readers (`new Resolver({resolvers: {}})`, so an external `$ref` becomes an `invalid-ref` finding with no I/O), but `@asyncapi/parser`'s `__unstable.resolver` CANNOT drop its default `http`/`https`/`file` readers (it always prepends them and falls through a custom resolver that throws). So: (1) `checker/src/refs.ts` pre-scans both the current document and `previousContent` for any `$ref` not starting with `#`, before either engine can resolve a reference. A current-document ref answers a SCHEMA ERROR `external-ref-not-allowed` (with the pointer), plus an INFO `asyncapi-diff-skipped` when an AsyncAPI comparison was requested. A baseline ref instead contributes an INFO `asyncapi-diff-skipped`: the candidate's own semantic and lint passes still run, saves are not blocked by an inaccessible historical dependency, and compatibility remains explicitly unknown. The iterative scan rejects cyclic aliases, limits traversal to 100 000 objects and depth 256, and unsafe YAML alias expansion becomes a deterministic finding/skip before an engine sees the text. (2) The container has **no route out**: compose puts it on `checker-net` (`internal: true`, no gateway, no host port), k8s puts it behind a ClusterIP + a `NetworkPolicy` (ingress from the app pod only, no egress). Verify layer 2 after a compose change: `docker compose exec checker wget -qO- https://example.com` must fail; `docker compose exec app wget -qO- http://checker:9090/healthz` must answer.

**Untrusted engine isolation.** Each admitted check runs in a fresh child process with a 96 MiB old-generation heap limit and 4 MiB stack limit. A parser's fatal V8 abort therefore cannot terminate the HTTP process. `CHECKER_TIMEOUT_MS` covers queueing and execution; at the deadline the parent sends `SIGKILL` and waits for child exit before answering 504. The 256 MiB deployment limit permits one child at a time (`CHECKER_MAX_CONCURRENT=1`); a FIFO holds eight ordinary parallel requests by default, and only overflow answers 503. The heap flag bounds V8 old-generation memory, while native/module RSS remains subject to the container's total limit. Per-request processes trade startup cost for a real crash and cancellation boundary. The HTTP process retains an injected in-process check function only for focused response-mapping tests.

**The JVM side (`contracts/checks/`).** `CheckerClient` is an interface (`check(type, content, previousContent): CheckerResponse`); `HttpCheckerClient` is the Ktor client (Java engine — no second Netty consumer; `HttpTimeout` at `checker.timeoutMs`; `X-Checker-Token`), published under `CheckerClientKey` by `configureChecks` (`application.yaml` `checker.url` — blank = disabled) unless a test pre-set the key (the `CatalogUrlFetcherKey` seam: tests install a `StubCheckerClient` with canned or throwing behaviour; `HttpCheckerClientTest` drives the real client against a 127.0.0.1 fixture). `ChecksService` calls it only for OPENAPI/ASYNCAPI, AFTER its own parse/type-gate/schema steps, and treats every failure (unreachable, timeout, non-2xx, malformed body) as one `SYSTEM WARN CHECKER_UNAVAILABLE` finding with `check_complete = false` on the stored version and an audit line `checker.unavailable` (byUserId + the request path, never the document) — **fail-open for lint, never for syntax/schema**. In production mode a blank `checker.url` logs a WARN at boot (not fail-closed: the JVM gates remain). `POST …/versions/{vid}/recheck` re-runs everything on the stored text — the operator's recovery after an outage.

**Local dev.** `cd checker && SCARF_ANALYTICS=false npm ci && npm run dev` (tsx watch, :9090) with `CHECKER_URL=http://localhost:9090 ./gradlew :server:run`; or `docker compose up postgres checker` and let the compose-internal address serve a compose-run app. Smoke from the repository root: `curl -s localhost:9090/healthz`; `node -e 'const fs=require("node:fs"); process.stdout.write(JSON.stringify({type:"OPENAPI",content:fs.readFileSync("checker/test/fixtures/openapi/petstore-3.1.yaml","utf8")}))' | curl -sS -XPOST localhost:9090/check -H 'content-type: application/json' --data-binary @-`. Gates: `npm run lint && npm run knip && npm run typecheck && npm run test:coverage && npm run build` (also `ci.yml`'s `checker` job). Review the internal HTTP contract with `npx --yes @stoplight/spectral-cli lint checker/openapi.yaml --ruleset api-guidelines/checker.spectral.yaml` from the repository root.

**Versions and bumps.** `@asyncapi/parser` pins its own `@stoplight/spectral-core` range — bump the parser first, then align the Spectral packages to the range it declares (they move together: core, parsers, ref-resolver, rulesets, types). Keep ONE vitest/typescript/eslint major across `web/`, `checker/` and `e2e/`. A ruleset bump can change verdicts: the fixture tests under `checker/test/fixtures/` pin expected findings per document, so a changed verdict fails there first; update the fixture consciously and note it in the changelog if user-visible.
