# Running, packaging, and deploying the covenant stack

## Packaging

Package the server for deployment with `./gradlew :server:installDist` (output under `server/build/install/server/`, launcher `bin/server`). **Do not use `:server:buildFatJar`** — the shadow plugin collapses the duplicate `META-INF/services/org.flywaydb.core.extensibility.Plugin` descriptors and the fat JAR NPEs at startup inside Flyway's plugin registry. `installDist` keeps each dependency JAR separate, so Flyway's `ServiceLoader` discovery works exactly as under `:server:run`.

## JVM footprint tuning

JVM footprint tuning is baked into the `application {}` block in `server/build.gradle.kts` via `applicationDefaultJvmArgs` = `-XX:+UseSerialGC -Xmx256m -XX:TieredStopAtLevel=1`, so it flows into both `bin/server` (→ Docker image) and `:server:run` (the Gradle `test` task is unaffected). Measured (in Lettuce, the same stack) on a 512 MiB Linux container: baseline G1 drifts **~345→410 MiB RSS** as it grows its heap, vs a steady, deterministic **~270 MiB** with these flags (**~25% lower and predictable**); startup is ~1.6 s either way, so the win is memory, not startup. SerialGC removes G1's per-heap overhead (~75 MiB); `-Xmx256m` caps a heap that holds no large caches (drop to `192m` to trim ~25 MiB more); C1-only (`TieredStopAtLevel=1`) trims code-cache + C2-compiler memory (~50 MiB) at the cost of peak CPU-bound throughput (irrelevant here — **remove that flag if the service ever runs hot**). Override per-deploy with `JAVA_OPTS`/`SERVER_OPTS` (the launcher appends both). Container ceilings match: `mem_limit: 512m` in `docker-compose.yaml`, `resources.limits.memory: 512Mi` (request `320Mi`) in `k8s/app-deployment.yaml`. This was evaluated (in Lettuce) instead of a GraalVM native-image migration, which the reflection/ServiceLoader-heavy stack (Ktor config modules, Flyway, Exposed, OTel, Logback, java-jwt) makes costly for little benefit on a long-running internal service.

## Running the full stack

Two ways to run, sharing the same `docker-compose.yaml`. All ports deliberately avoid Lettuce's (8080/5432/5173/8025) and Toadie's (8081/5433/5174/8026), so the three stacks can run side by side on one machine; host ports bind to 127.0.0.1:

- **One command (clone & run / demo):** `docker compose up --build` builds the SPA, the server and the checker sidecar, starts PostgreSQL, runs Flyway on boot, and serves everything at `http://localhost:8082` (Swagger at `/openapi`; sign in as `admin@covenant.local` / `changeme`; Mailpit at `http://localhost:8027`). The checker sits on the `checker-net` internal network only — no host port, no route out (`docker compose exec checker wget -qO- https://example.com` must FAIL; `docker compose exec app wget -qO- http://checker:9090/healthz` must answer). Tear down with `docker compose down` (add `-v` to drop the DB volume).
- **Local development (hot reload):** in separate terminals, run `docker compose up postgres mailpit` (Postgres host port **5434** → in-container 5432), `cd checker && npm run dev` (source checker on **9090**), `CHECKER_URL=http://localhost:9090 ./gradlew :server:run`, and `cd web && npm run dev` (Vite on **5175**, proxying `/api` → **8082**). The Compose checker has no host port, so it cannot serve a host-run JVM. Without a reachable checker the server still runs; contract checks carry a `CHECKER_UNAVAILABLE` finding.

- **Local Kubernetes (OrbStack):** give each local build a unique tag, for example `COVENANT_IMAGE_TAG="dev-$(git rev-parse --short=12 HEAD)-$(date +%s)"`, then run `docker build -t "covenant-app:${COVENANT_IMAGE_TAG}" .` and `docker build -t "covenant-checker:${COVENANT_IMAGE_TAG}" -f checker/Dockerfile .`. Create the `covenant` namespace and `covenant-secrets` Secret (command in `k8s/secret.yaml`), then run `./k8s/apply-local.sh "$COVENANT_IMAGE_TAG"`. The script renders both deployments with that tag *before* applying any resource and deliberately excludes the Secret template. The checked-in `:local-build` names are render placeholders; never apply the directory directly. Unique tags make `imagePullPolicy: IfNotPresent` deterministic while OrbStack's cluster shares Docker's image store, so no push is needed. Everything lives in the dedicated namespace so it coexists with Lettuce and Toadie. The checker remains behind a ClusterIP service and a `NetworkPolicy` allowing ingress from the app pod only and no egress at all, the k8s twin of the compose internal network. PostgreSQL uses an exact version and multi-platform manifest digest, its argv-list exec probe also serves as the readiness gate, and the app service is `type: LoadBalancer` (or use `kubectl -n covenant port-forward svc/app 8082:8082`). **Teardown:** retain database data by scaling the three deployments to zero, or delete the deployments, services and NetworkPolicy explicitly while leaving the `postgres-data` PVC intact. Delete that PVC only when its data is no longer needed; the `local-path` storageclass reclaim policy deletes the backing volume. **Secrets:** the deployments consume the `covenant-secrets` Secret via `secretKeyRef` (`JWT_SECRET`, `POSTGRES_USER`/`POSTGRES_PASSWORD`, `ADMIN_INITIAL_PASSWORD`, the optional `CHECKER_TOKEN`); `k8s/secret.yaml` is a placeholder **template** — applying it verbatim fail-closes at startup (the placeholder JWT value is on the burned list in `plugins/Security.kt`). The app deployment runs production mode (`KTOR_DEVELOPMENT=false`, `HTTP_BEHIND_PROXY=true` — it expects a TLS-terminating ingress that sets `X-Forwarded-For`/`-Proto`); for throwaway plain-HTTP local-cluster testing, flip `KTOR_DEVELOPMENT` to `"true"` in `k8s/app-deployment.yaml`.

The root `Dockerfile` is a 3-stage build: (1) Node 24.21.0 builds `web/dist` (`npm ci --legacy-peer-deps`), (2) Temurin 21.0.12+8 JDK on Ubuntu 24.04 Noble runs `:server:installDist`, (3) the matching Temurin JRE bundles the install image **and** the built SPA, sets `WEB_STATIC_DIR=/app/web` and `KTOR_DEVELOPMENT=false`, and runs `bin/server`. Every external base uses an exact tag and reviewed multi-platform manifest digest; naming Noble explicitly avoids the default Temurin tag moving the base OS to Ubuntu 26.04. The local mise identifier `temurin-21.0.12+101.0.LTS` maps to Adoptium's 21.0.12.1+1 CSPU; mise's `+101` spelling is its catalog encoding of the upstream `.1+1` version. The official Temurin container repository had not published that CSPU when these pins were reviewed, so the Docker bases remain on the newest container release actually available and runtime-probed, 21.0.12+8; update both JDK and JRE together once the CSPU images exist. The `app` Compose service points the `POSTGRES_*` env vars at the `postgres` service host (`postgres:5432` in-network), `CHECKER_URL` at `http://checker:9090`, and waits on both healthchecks. Compose and Testcontainers share PostgreSQL 18.6's reviewed digest; Mailpit is pinned to the security-fixed 1.31.2 image. `checker/Dockerfile` is a 2-stage Node build (npm ci → tsc → `npm prune --omit=dev`; runtime as the `node` user with a read-only root filesystem). `.dockerignore` keeps build outputs / `node_modules` (web, checker, e2e) out of the build context; `.git` is **included** on purpose — the SPA build stage reads the commit sha/timestamp from it for the version stamp (see "Build version stamp" in `web/CLAUDE.md`). Note the volume mount: postgres 18+ images keep data in a versioned subdir of `/var/lib/postgresql`, so the compose volume mounts that path (the pre-18 `/var/lib/postgresql/data` path makes the container unhealthy).
